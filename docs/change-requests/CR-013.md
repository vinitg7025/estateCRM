# CR-013: Host on Vercel as one project with Vercel Services (instead of 7 projects)

| | |
|---|---|
| Raised | 2026-09-30, by the product owner (Vercel suggested Services when the repo was imported) |
| Affects | HLD §9/§10 hosting and ADR-0002 (7 Vercel projects), `docs/04-lld/data-hosting.md` (per-project env), provisioning runbook |
| Status | **AWAITING `APPROVED: CR-013`**. Configuration choices confirmed by the product owner on 2026-09-30 (below) |

## What
Deploy all seven apps as **one Vercel project** using Vercel Services (beta, available on Hobby), defined in the root
`vercel.json`:
- **Services:** `web` (Next.js) plus `intake`, `records`, `journeys`, `crm-engine`, `listings` and `insight` (Hono preset, entry
  `services/<svc>/index.ts`). All in region `bom1`, 60 s functions, pnpm 12.7.0.
- **Public routes (top-level rewrites), all other paths internal:**
  - `/public/v1/{listings,projects,demand-posts,changes}…` → listings. The website API: `/public` is stripped by a
    `request.path` transform, and `X-Api-Key` is still required.
  - `/svc/<svc>/internal/v1/{relay,drain/…,jobs/…}` and `/svc/<svc>/health/…` → that service. Supabase pg_cron uses these;
    `/svc/<svc>` is stripped and `X-Cron-Secret` is still required.
  - everything else → web.
- **Bindings** (private calls; Vercel injects the URL): web → all six (`SVC_<SERVICE>_URL`); intake → records; records →
  intake; journeys → records, listings, intake; crm-engine → records, journeys; listings → records; insight → records; every
  service → web (`WEB_URL`: JWKS and service tokens). The existing env names are used, so there were no code changes for bindings.

## Why
- One domain and one deployment: previews include all seven services at the same commit. Internal services are not
  reachable from the internet at all, which is stronger than the 7-project design, where every service had a public URL.
- Simpler provisioning: one project instead of seven.

## Decisions confirmed by the product owner (2026-09-30)
1. Website API path: `/public/v1/…` on the app domain.
2. Scheduler access: `/svc/<service>/internal/…` with the per-service cron secret. The scheduler stays in Supabase pg_cron,
   because Vercel Cron on Hobby runs at most once a day and the event relays need every minute. Revisit at the paid gate.
3. Service names = folder names.
4. Bindings as listed above.

## Impact
- `services/<svc>/vercel.json` and `api/index.ts` are removed; each service has `index.ts` (default export of the composed
  Hono app). The scaffold generator is updated.
- Environment variables are shared across services in one project: only prefixed per-service names are allowed
  (`RECORDS_DATABASE_URL`, …), as the runbook says. data-hosting §3 ("one DATABASE_URL per Vercel project") is superseded
  by this rule.
- Scheduler base URLs become `https://<domain>/svc/<service>` (`configure-environment.mjs` unchanged).
- Risks: Services is in beta. `vercel dev` couldn't start all 7 locally (its dependency installer crashed), so local dev
  stays `pnpm dev`, and the first preview deployment validates the routing. Fallback: 7 separate projects (the previous
  design); the service code is the same, and only config would change.

## Revision 2026-10-02 (first deployments)
Findings from the first production deployments of the one-project setup (`estatecrm`, production domain
`estatecrm-navy.vercel.app`). Still **AWAITING `APPROVED: CR-013`**; approval now covers this revision.

1. **Backend entry is a bundled ES module.** Vercel's function bundle does not include the service's `package.json`, so
   Node loaded `index.js` as CommonJS and every backend failed on its first `import` (`FUNCTION_INVOCATION_FAILED`).
   Each service's build now runs `pnpm bundle:vercel` (`tools/bundle-service.mjs`, esbuild): `index.ts` → one
   self-contained `dist/vercel/app.mjs`. The Vercel entrypoint is the tracked `services/<svc>/vercel.mjs`, which
   re-exports it. `.mjs` is ESM regardless of `package.json`. pdfkit's standard fonts (journeys proposal PDFs) are
   inlined by a small esbuild plugin. Verified locally from an empty folder: all six answer `/health/live`, a proposal PDF
   and an Excel export render. The scaffold generator creates `vercel.mjs` and the script for new services.
2. **Bindings as configured.** Vercel rejects cycles, so the bindings differ from "Bindings" above:
   - web → intake, records, journeys, crm-engine, listings, insight (`SVC_<SERVICE>_URL`)
   - records → intake; journeys → records, listings, intake; crm-engine → records, journeys; listings → records;
     insight → records (`<SERVICE>_URL`)
   - **Removed:** every service → web (cycle with web → all). `WEB_URL` is set instead as a project variable (the app's
     production URL); the services reach web's JWKS and service-token endpoints through it.
   - **Removed:** intake → records (cycle with records → intake, which records needs to read upload rows). intake's
     records client is therefore off. Effect: uploads keep working on the active vocabulary release, but locality
     lookup is skipped, and a new `vocabulary.released.v1` cannot be fetched (that event goes to intake's DLQ with an
     alarm). **Open point:** restore the call (cyclic bindings if Vercel allows them, or a route through web) before the
     first vocabulary release after v0.6 and before locality matching matters in the pilot.
3. **Required per-service secrets** (Sensitive, Production) beyond database URLs and cron secrets, found while testing
   the bundles: `INTAKE_ANONYMISATION_KEY`, `RECORDS_CONTACT_HASH_SECRET`, `RECORDS_SCAN_SALT` and `LISTINGS_SCAN_SALT` (the same
   value: listings checks records' scan-term hashes, R-20),
   `JOURNEYS_IP_HASH_SALT`, the six `<SERVICE>_SERVICE_CREDENTIAL` (from `pnpm --filter @11e/web service-client <svc>`),
   and `RECORDS_STORAGE_SERVICE_KEY` / `LISTINGS_STORAGE_SERVICE_KEY` with `RECORDS_STORAGE_URL` / `LISTINGS_STORAGE_URL`.
4. Vercel Authentication (standard protection) does not block the production domain, so pg_cron can call
   `/svc/<svc>/internal/…` there.

## Revision 2026-10-02 (b): restore intake → records (option 1)
Resolves the open point in revision (a), item 2. Still **AWAITING `APPROVED: CR-013`**; approval covers this revision.

- **Route:** one new public rewrite, `/svc/records/v1/(micromarkets|vocabulary)` → records (the two endpoints intake's records
  client calls: `GET /v1/micromarkets`, `GET /v1/vocabulary`). It is placed before the catch-all and uses the existing
  `/svc/records` prefix-strip transform.
- **Wiring:** no new binding (Vercel rejects the intake ↔ records cycle). intake gets `INTAKE_RECORDS_URL` as a plain
  project variable: `https://estatecrm-navy.vercel.app/svc/records`. The prefixed name is required because a bare
  `RECORDS_URL` would clash with the binding Vercel injects into other services.
- **Security trade-off:** these two read endpoints are now reachable from the internet. They still require a service token
  for `records` (a Bearer token minted by web, tenant-scoped) and records re-checks it; no other records path is exposed.
  This weakens the "internal services are not reachable" property for these two paths only.
- **Revisit:** before wider use, remove the cycle properly (intake pushes rows to records, or the vocabulary release carries its
  content) and drop this rewrite.
